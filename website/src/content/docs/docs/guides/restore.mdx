<Aside type="danger">A restore **replaces** the data currently in the database. VigilOps takes a safety backup first, so you can undo it, but double-check the container name before confirming.</Aside>

## Restore

<Steps>

1. **Find the backup:**

   ```bash
   vigil backups myapp-postgres
   ```

   ```
   🗄  BACKUPS in /var/backups/vigil

      myapp-postgres__myapp__20260916-020000.sql.gz
         48.2 MB — 16/09/2026, 02:00:12
   ```

2. **Restore it:**

   ```bash
   vigil restore myapp-postgres__myapp__20260916-020000.sql.gz
   ```

   Type `yes` when asked. From Telegram, send `/restore <file>` and tap **Yes, restore**.

</Steps>

What happens:

1. VigilOps looks for the file in `/var/backups/vigil/`. If it isn't there and [off-server storage](/docs/guides/offsite-storage/) is configured, it downloads the file.
2. It backs up the current database as `<container>__<database>__<time>_pre-restore.sql.gz`.
3. It loads the backup into the database named in the file name, inside the container named in the file name.

If step 3 fails, the database may be partly restored. Restore the `_pre-restore` backup to get back to where you started.

## Undo a restore

Every restore takes a safety backup of the target first, so the last one can be reversed:

```bash
vigil undo
```

It shows what it would reverse and asks before doing anything:

```
↩️  Last reversible action: restore of myapp in myapp-postgres (12 min ago)
    — would put back the safety backup taken first

Undo it? Type "yes" to continue:
```

The undo itself takes a safety backup too, so it can be reversed in turn. `vigil undo` also reverses the last deploy, whichever happened most recently.

To pick a specific point instead, restore the safety backup by name:

```bash
vigil backups myapp-postgres        # the newest ..._pre-restore file
vigil restore myapp-postgres__myapp__20260916-101500_pre-restore.sql.gz
```

## Restore into a different container

Add the target container. For example, copy production data into staging:

```bash
vigil restore myapp-postgres__myapp__20260916-020000.sql.gz myapp-staging-postgres
```

Restoring into a **different** container uses that container's own database, so production data lands in staging's database (`myapp_staging`), not one named after production. VigilOps prints the database it will overwrite before asking you to confirm.

To choose the database yourself, name it after the container:

```bash
vigil restore myapp-postgres__myapp__20260916-020000.sql.gz myapp-staging-postgres myapp_test
```

Restoring onto the **same** container always uses the database named in the file.

## Restore on a new server

If the original server is gone:

<Steps>

1. [Install VigilOps](/docs/install/) on the new server and start your database container.

2. **Get the backup file onto the new server.** Either:
   - **From object storage:** use the same `BACKUP_S3_*` settings, and set `BACKUP_S3_PREFIX` to the old server's folder (`vigil/<old-hostname>`). `vigil restore <file>` downloads it automatically.
   - **From Telegram:** download the file from the chat to your computer, then upload it:

     ```bash
     scp myapp-postgres__myapp__20260916-020000.sql.gz root@new-server:/var/backups/vigil/
     ```

3. **Restore**, naming the new container if its name changed:

   ```bash
   vigil restore myapp-postgres__myapp__20260916-020000.sql.gz
   ```

</Steps>

## Skip the confirmation

For scripts, add `--yes`:

```bash
vigil restore <file> [container] [database] --yes
```

## Test that a backup really restores

A backup you've never restored is only a hope. One command restores the newest backup into a throwaway container and reports what arrived:

```bash
vigil restore test myapp-postgres
```

```
🧪 Testing a restore of myapp-postgres
   Nothing touches your live database: the backup is loaded into a
   throwaway container with no network, which is removed afterwards.

   File:     myapp-postgres__myapp__20261013-020032.sql.gz (193.8 MB)
   Restored: postgres:17-alpine in 137s
   Tables:   131 (live has 131)

   Rows in the largest tables:
      public.analytics_stream_facts_default             1,229,803  = live
      public.royalty_data                                 764,968  = live

✅ This backup restores.
```

Pass a file name instead of a container to test a specific backup.

**Nothing touches your live database.** The copy runs in its own container, started from the same image your database uses, with a generated password, `--network none`, no volume, and removal at the end even if the restore fails. Your live database is only ever read, to compare counts against.

**Exit code 0 is not the check.** A dump can load cleanly and be empty, which is the failure that actually bites — a backup quietly capturing nothing for weeks. So it compares table counts against the live database and row counts for the five largest tables, and fails when the restore is empty or a table that has rows live comes back empty.

It needs free disk of about twice the backup size, and it costs real CPU and memory while it runs, so prefer a quiet hour on a busy server. `--keep` leaves the test container running if you want to poke at it yourself.

Exit status is `0` when the backup restores and `1` when it doesn't, so it works in a cron job or CI.
